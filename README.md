# ROS Bridge GRPC

This project began as an attempt to remedy some of the build and compatibility issues seen by the popular [ros1_bridge](https://github.com/ros2/ros1_bridge) package. As it evolved, more functionality was added until it now represents a general and flexible bridge bewteen basically any two versions of ROS. It does this by doing away with the structure of compiling both ROS1 and ROS2 on a single system, and instead builds Docker images for each platform separately and bridges them locally with gRPC. gRPC is a network messaging system similar to ROS, and indeed is one of the main alternatives seen in practice. Crucially, it is not tied to any specific OS or software release, and so we can compile message definitions which work for both the ROS1 and ROS2 Docker systems.

It's worth noting that this structure does come with a cost. Whereas the original `ros1_bridge` would pass a message from ROS1 to ROS2 (or vice versa) with the structure 

```ros1_publisher -> [deserialize ros1] -> [serialize ros2] -> ros2_publisher```

we now have to perform an additional serialization/deserialization step since we've introduced a new format to the mix. So data passage instead looks like

```ros1_publisher -> [deserialize ros1] -> [serialize protobuf] -> [deserialize protobuf] -> [serialize ros2] -> ros2_publisher```.

However, with this performance hit we buy stability across new ROS distros and operating systems.

**NOTE** Currently, ROS Bridge GRPC only bridges topics and services, not actions. The underlying architecture should work well for this use case though, so actions may be added in the future.

## How it works

The code generation pipeline starts on the ROS2 side. All configured message types are installed and sourced in the ROS2 workspace. `ros_bridge_grpc` then leverages the `rclpy` suite of code introspection functions to examine the message definitions and generate protobuf message and service definitions which match the ROS message type definition. Note that there are some limitations here, as the interfaces for ROS and gRPC are somewhat different, and so not all message features and field data types can be respected.

The protobuf message files are then passed to the protoc compiler to generate both protobuf and gRPC C++ library code. These message and library files will be shared by both sides of the bridge to ensure compatibility, and are used by both the ROS1 and ROS2 docker systems to create C++ functions which convert seamlessly between ROS(1/2) and gRPC. These conversion functions also include the necessary calls in either ROS1 or ROS2 to generate ROS subscribers and publishers and connect them to their gRPC counterparts.

The second docker system (either ROS1 or ROS2) then parses the protobuf message definition files generated by the original docker system, and cross-references them against its own native message definitions. Messages with non-equivalent fields, datatypes, constants, or sizes are rejected as incompatible, with the option to manually override this for certain message types (for instance `std_msgs/Header` can be overridden as the `seq` field was removed in ROS2). ROS2 introduced many array size constraints which are not present in ROS1 or gRPC. For these cases, we simply mark them as compatible as long as the field is an array on both sides, and we let the ROS2 side of the bridge handle sanitizing array lengths.

## Installation

The first and only major step is to install docker. You can follow along with the [official installation instructions](https://docs.docker.com/engine/install/) to make sure you have the most up-to-date version on your system.

The package is designed to do the heavy work for you, so all you have to do is fill out your desired bridge configuration and docker will do the rest. Here's the general format of a config file:

```yaml
side_A_distro: jazzy # side_A must always be ROS2
side_B_distro: noetic

msg_packages:
    std_msgs/msg: [String]
    tf2_msgs/msg: [ALL]
    geometry_msgs/msg: [PoseWithCovarianceStamped]
    sensor_msgs/msg: [PointCloud2, Image, CameraInfo]
    moveit_msgs/msg: [JointLimits, SolidPrimitive]
    std_srvs/srv: [Trigger, SetBool]
    bridge_interface_example/srv: [ALL]

custom_packages:
    - {package_name: bridge_interface_example,
        side_A_path: ./../ros2/bridge_interface_example,
        side_B_path: ./../ros1/bridge_interface_example}

    - {package_name: moveit_msgs,
        side_A_url: https://github.com/moveit/moveit_msgs.git -b humble,
        side_B_url: https://github.com/moveit/moveit_msgs.git -b ros2}

compatibility_overrides:
    - "std_msgs/msg/Header"              # Has seq field in ROS1 but not in ROS2
    - "shape_msgs/msg/SolidPrimitive"    # Has new enum constants added in ROS2
    - "moveit_msgs/msg/JointLimits"      # Has jerk related fields in ROS2 but not ROS1
    - "moveit_msgs/srv/GetCartesianPath" # Introduced a new link speed limit field in ROS2 iron  
    - "moveit_msgs/msg/MoveItErrorCodes" # Introduced a new message and source fields in ROS2 jazzy

```

Once you have all your desired message packages properly configured, navigate to the `docker` folder in this repo and run 

```bash
export ROS_BRIDGE_BUILD_CONFIG=</path/to/your/config/file>
source build.sh
```

Your docker images should build, which will take at least 10 minutes, but potentially much more depending on how many message types you configured to be baked in. 

## Running the Bridge

Once complete, you can configure your runtime settings in a separate yaml file which lists the topics and types that you want to bridge. For example:

```yaml
# === Messages ===
registered_topics: 
  - /robot_description
  - /velodyne_points
  - /my_robot/joint_states
  - /tf
  - /tf_static

/robot_description: 
  type: std_msgs/msg/String
  transient_local: true

/velodyne_points:
  type: sensor_msgs/msg/PointCloud2
  best_effort: true

/my_robot/joint_states:
  type: sensor_msgs/msg/JointState
  best_effort: true

/tf:
  type: tf2_msgs/msg/TFMessage
  
/tf_static:
  type: tf2_msgs/msg/TFMessage
  transient_local: true

# === Services ===
registered_services:
  - /start_behavior_tree

/start_behavior_tree:
  type: std_srvs/srv/Trigger
  side_a_role: client
  side_b_role: service

# === Networking ===
side_a_server_address: /tmp/side_a_server.sock
side_b_server_address: /tmp/side_b_server.sock
```
Navigate to the `docker` folder of this repo, and run the following commands:

```bash
export ROS_BRIDGE_RUNTIME_CONFIG=<path/to/your/runtime/config>
source runtime.sh
docker compose --profile runtime up
```

Note that the following runtime settings for ROS1 and ROS2 are read directly from your environment:
 * `ROS_DOMAIN_ID`
 * `RMW_IMPLEMENTATION`
 * `CYCLONEDDS_URI`
 * `ROS_MASTER_URI`
 * `ROS_HOSTNAME`
 * `ROS_IP`

If any of these values need to be modified on a per-bridge basis, this can be done by editing the `config/side_a.env` and `config/side_b.env` files.

And that's it! You should be good to go to pass messages seamlessly between any two versions of ROS.

## Running ROS1/ROS2 Development Environments

Quickly launch interactive shell environments for ROS1 or ROS2 (useful for rosbag playback, RViz, testing, and development). The services are defined in `docker-compose.yaml` as `side_a_bridge_dev` and `side_b_bridge_dev`.

On a new terminal, export the same build/runtime environment variables from before. Then:

```bash
# Start dev shells (detached)
docker compose run --rm side_a_bridge_dev # or side_b_bridge_dev

# Stop and remove the dev containers
docker compose --profile dev down
```

Once the container is running, attach to it with:
```bash
# Attach to ROS dev shell
docker exec -it ros1_bridge_dev bash  # or ros2_bridge_dev
```


## Advanced Use Cases

ROS Bridge GRPC was conceptualized as a joint program intended to run on a single machine to bridge ROS1 and ROS2 communications. However, the resulting framework is quite versatile, and allows for some interesting possibilities:

 * **Running Remotely** - It is possible to run the two halves of the bridge on different machines since gRPC, much like ROS, is a networked communication framework. In this case, you must explicitly tell each client which IP address it should look to for a matching server instead of just the default `localhost`. This parameter can be set in the runtime config shown above. Add an entry for `grpc_server_address` and set it to the local IP address (or the catchall `0.0.0.0`) along with a port number. Eg. `0.0.0.0:<your_port_number>`. Then add an entry for `grpc_client_address` and set it to the IP address and port number of the other computer. Repeat the steps on the other computer with the addresses flipped.
 ```yaml
 grpc_address_1: 192.168.0.101:20002
 grpc_address_2: 192.168.0.108:20003
 ```

 * **Running Natively** - There's nothing stopping either of bridge halves from being built and installed natively instead of through docker. Indeed, that's how initial testing and development on this project were performed. Instead of providing detailed instructions on how to do this, we ask you instead follow along the Dockerfile to see how it is done there and adapt it for your machine.

 * **gRPC Application** - Once either bridge side receives a ROS2 message, it republishes it as a gRPC message and vice-versa. As such, you can directly integrate the code from this project into an existing gRPC project to eliminate the middle man and have direct communication between ROS and gRPC networks.

 * **ROS2 - ROS2 Bridge** - Each half of the bridge is completely independent except for the gRPC connection, and so this project can be used to bridge two different ROS1 or ROS2 networks. While in general it's better to try to get your entire project on one network, there may be cases in which there is a need to bridge previously isolated networks. With this, you can bridge ROS2 networks on different ROS_DOMAIN_ID's, on different network interfaces, or on different middleware implementations.
