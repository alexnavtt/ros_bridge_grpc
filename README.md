# ROS1 Bridge GRPC

This project represents an attempt to remedy some of the build and compatibility issues seen by the popular [ros1_bridge](https://github.com/ros2/ros1_bridge) package. It does this by doing away with the structure of compiling both ROS1 and ROS2 on a single system, and instead builds Docker images for each platform separately and bridges them locally with gRPC. gRPC is a network messaging system similar to ROS, and indeed is one of the main alternatives seen in practice. Crucially, it is not tied to any specific OS or software release, and so we can compile message definitions which work for both the ROS1 and ROS2 Docker systems.

It's worth noting that this structure does come with a cost. Whereas the original `ros1_bridge` would pass a message from ROS1 to ROS2 (or vice versa) with the structure 

```ros1_publisher -> [deserialize ros1] -> [serialize ros2] -> ros2_publisher```

we now have to perform an additional serialization/deserialization step since we've introduced a new format to the mix. So data passage instead looks like

```ros1_publisher -> [deserialize ros1] -> [serialize protobuf] -> [deserialize protobuf] -> [serialize ros2] -> ros2_publisher```.

However, with this performance hit we buy stability across new ROS distros and operating systems.

**NOTE** Currently, ROS1 Bridge GRPC only bridges topics, not services or actions. The underlying architecture should work well for these use cases though, so it's likely that services and actions will be added in the future.

## How it works

The code generation pipeline starts on the ROS2 side. All configured message types are installed and sourced in the ROS2 workspace. `ros1_bridge_grpc` then leverages the `rclpy` suite of code introspection functions to examine the message definitions and generate protobuf message and service definitions which match the ROS message type definition. Note that there are some limitations here, as the interfaces for ROS and gRPC are somewhat different, and so not all message features and field data types can be respected.

The protobuf message files are then passed to the protoc compiler to generate both protobuf and gRPC C++ library code. These message and library files will be shared by both the ROS1 and ROS2 sides of the bridge to ensure compatibility, and are used by both the ROS1 and ROS2 docker systems to create C++ functions which convert seamlessly between ROS(1/2) and gRPC. These conversion functions also include the necessary calls in either ROS1 or ROS2 to generate ROS subscribers and publishers and connect them to their gRPC counterparts.

The ROS1 docker system then parses the protobuf message definition files generated by the ROS2 docker system, and cross-references them against the native ROS1 message definitions. Messages with non-equivalent fields, datatypes, constants, or sizes are rejected as incompatible, with the option to manually override this for certain message types (for instance `std_msgs/Header` is always overridden as the `seq` field was removed in ROS2). ROS2 introduced many array size constraints which are not present in ROS1 or gRPC. For these cases, we simply mark them as compatible as long as the field is an array on both sides, and we let the ROS2 side of the bridge handle sanitizing array lengths.

## Installation

The first and only major step is to install docker. You can follow along with the [official installation instructions](https://docs.docker.com/engine/install/) to make sure you have the most up-to-date version on your system.

The package is designed to do the heavy work for you, so all you have to do is fill out your desired bridge configuration and docker will do the rest. Here's the general format of a config file:

```yaml
ros1_distro: noetic
ros2_distro: humble

msg_packages:
    std_msgs: [ALL]

    geometry_msgs:
        - Point
        - Pose
        - PoseStamped

    sensor_msgs:
        - PointCloud2

custom_packages:
    - {package_name: my_package,
       ros1_url: "https://github.com/my_org/my_package.git -b noetic",
       ros2_url: "https://github.com/my_org/my_package.git -b humble"}
    - {package_name: my_other_package,
       ros1_url: "git@github.com:my_org/my_other_package.git",
       ros2_url: "git@github.com:my_org/my_other_package.git -b ros2"}
    - {package_name: local_package,
       ros1_path: "/local/path/to/my/awesome/ros1/interface_package",
       ros2_path: "/local/path/to/my/awesome/ros2/interface_package"}
    - {package_name: local_package_dependency,
       ros1_path: "/local/path/to/my/non_rosdep/ros1/interface/package/dependency",
       ros2_path: "/local/path/to/my/non_rosdep/ros2/interface/package/dependency"}

compatibility_overrides:
    - "std_msgs/Header"
```

Once you have all your desired message packages properly configured, navigate to the `docker` folder in this repo and run 

```bash
export ROS_BRIDGE_BUILD_CONFIG=</path/to/your/config/file>
source build.sh
```

Your docker images should build, which will take at least 10 minutes, but potentially much more depending on how many message types you configured to be baked in. 

## Running the Bridge

Once complete, you can configure your runtime settings in a separate yaml file which lists the topics and types that you want to bridge. For example:

```yaml
registered_topics: 
  - /my_string_topic
  - /velodyne_points
  - /my_robot/joint_states
  - /tf
  - /tf_static

/my_string_topic: 
  type: std_msgs/String

/velodyne_points:
  type: sensor_msgs/PointCloud2
  best_effort: false

/my_robot/joint_states:
  type: sensor_msgs/JointState
  best_effort: true

/tf:
  type: tf2_msgs/TFMessage
  
/tf_static:
  type: tf2_msgs/TFMessage
  transient_local: true

ros1_server_address: localhost:50051
ros2_server_address: localhost:50052

# Alternately with unix sockets
# Note that the .sock extension is required for this to work
# /tmp is mounted to the docker images by default, but you can add others if you wish
ros1_server_address: /tmp/ros1_server.sock
ros2_server_address: /tmp/ros2_server.sock
```
Navigate to the `docker` folder of this repo, and run the following commands:

```bash
export ROS_BRIDGE_RUNTIME_CONFIG=<path/to/your/runtime/config>
export ROS_BRIDGE_GRPC_ROS1_DISTRO=<your_ros1_distro>
export ROS_BRIDGE_GRPC_ROS2_DISTRO=<your_ros2_distro>
docker compose --profile runtime up
```

Note that the following runtime settings for ROS1 and ROS2 are read directly from your environment:
 * `ROS_DOMAIN_ID`
 * `RMW_IMPLEMENTATION`
 * `CYCLONEDDS_URI`
 * `ROS_MASTER_URI`
 * `ROS_HOSTNAME`
 * `ROS_IP`

And that's it! You should be good to go to pass messages seamlessly between ROS1 and ROS2.

## Advanced Use Cases

ROS1 Bridge GRPC was conceptualized as a joint program intended to run on a single machine to bridge ROS1 and ROS2 communications. However, the resulting framework is quite versatile, and allows for some interesting possibilities:

 * **Running Remotely** - It is possible to run the two halves of the bridge on different machines since gRPC, much like ROS, is a networked communication framework. In this case, you must explicitly tell each client which IP address it should look to for a matching server instead of just the default `localhost`. This parameter can be set in the runtime config shown above. Add an entry for `grpc_server_address` and set it to the local IP address (or the catchall `0.0.0.0`) along with a port number. Eg. `0.0.0.0:<your_port_number>`. Then add an entry for `grpc_client_address` and set it to the IP address and port number of the other computer. Repeat the steps on the other computer with the addresses flipped.
 ```yaml
 grpc_address_1: 192.168.0.101:20002
 grpc_address_2: 192.168.0.108:20003
 ```

 * **Running Natively** - There's nothing stopping either of bridge halves from being built and installed natively instead of through docker. Indeed, that's how initial testing and development on this project were performed. Instead of providing detailed instructions on how to do this, we ask you instead follow along the Dockerfile to see how it is done there and adapt it for your machine.

 * **gRPC Application** - Once either bridge side receives a ROS2 message, it republishes it as a gRPC message and vice-versa. As such, you can directly integrate the code from this project into an existing gRPC project to eliminate the middle man and have direct communication between ROS and gRPC networks.

 * **ROS2 - ROS2 Bridge** - Each half of the bridge is completely independent except for the gRPC connection, and so this project can be used to bridge two different ROS1 or ROS2 networks. While in general it's better to try to get your entire project on one network, there may be cases in which there is a need to bridge previously isolated networks. With this, you can bridge ROS2 networks on different ROS_DOMAIN_ID's, on different network interfaces, or on different DDS implementations. This requires that you instead run the ROS2 bridge twice with different settings. Instead of running `docker compose up` in this case it is better to run as `docker compose run --rm ros2_bridge` with the appropriate setting sourced to the bash environment.

**NOTE:** While it is completely feasible to run two ROS2 bridges from different ROS2 distros, there is currently no check in the bridge build process to ensure compatibility between message definitions from one release to the next, just between the configured ROS1 and ROS2 distros. Therefore there is no guarantee of compatibility in these cases. For stable message types like `sensor_msgs` it will likely work fine, but for actively developed packages like `moveit_msgs` there will almost definitely be incompatibilities between versions. ROS2 bridge compatibility will be implemented in the future.
