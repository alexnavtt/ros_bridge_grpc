# ROS1 Bridge GRPC

This project represents an attempt to remedy some of the build and compatibility issues seem by the popular [ros1_bridge](https://github.com/ros2/ros1_bridge) package. It does this doing away with the structure of compiling both ROS1 and ROS2 on a single system, and instead builds Docker images for each platform separately and bridges them locally with gRPC. gRPC is a network messaging system similar to ROS, and indeed is one of the main alternatives seen in practice. Cruically, it is not tied to any specific OS or software release, and so we can compile message definitions which work for both the ROS1 and ROS2 Docker systems.

It's worth noting that this structure does come with a cost. Whereas the original `ros1_bridge` would pass a message from ROS1 to ROS2 (or vice versa) with the structure 

```ros1_publisher -> [deserialize ros1] -> [serialize ros2] -> ros2_publisher```

we now have to perform an additional serialization/deserialization step since we've introduced a new format to the mix. So data passage instead looks like

```ros1_publisher -> [deserialize ros1] -> [serialize protobuf] -> [deserialize protobuf] -> [serialize ros2] -> ros2_publisher```.

However, with this performance hit we buy stability across new ROS distros and operating systems.

## How it works

The code generation pipeline starts on the ROS2 side. All configured message types are installed **[TODO: Figure out custom message types]** and sourced in the ROS2 workspace. `ros1_bridge_grpc` then leverages the `rclpy` suite of code introspection functions to examine the message definitions and generate protobuf message and service definitions which match the ROS message type definition. Note that there are some limitations here, as the interfaces for ROS and gRPC are somewhat different, and so not all message features and field data types can be respected.

The protobuf message files are then passed to the protoc compiler to generate both protobuf and gRPC C++ library code. These message and library files will be shared by both the ROS1 and ROS2 sides of the bridge to ensure compatibility, and are used by both the ROS1 and ROS2 docker systems to create C++ functions which convert seamlessly between ROS(1/2) and gRPC. These conversion functions also include the necessary calls in either ROS1 or ROS2 to generate ROS subscribers and publishers and connect them to their gRPC counterparts.

The ROS1 docker system then parses the protobuf message definition files generated by the ROS2 docker system, and cross-references them against the native ROS1 message definitions. Messages with non-equivalent fields, datatypes, constants, or sizes are rejected as incompatible, with the option to manually override this for certain message types (for instance `std_msgs/Header` is always overridden as the `seq` field was removed in ROS2). ROS2 introduced many array size constraints which are not present in ROS1 or gRPC. For these cases, we simply mark them as compatible as long as the field is an array on both sides, with the assumption that the ROS2 client or server will be sending valid messages.
